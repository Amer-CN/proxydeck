# 团结（Codely）反代从封号到整改的全过程复盘

> ⚠️ **重要声明**：本文档只记录 **我们自己的修复方式和推理逻辑**，**不是绝对答案**。
> 我们没有官方内部资料，所有结论来自：逆向官方 CLI 源码（@unity-china/codely-cli rc.54）、
> 抓包实证、真实流量反复试错。群里每位开发者的环境不同，请以你的实测为准。
> 如果这些经验能帮你们少走弯路，或者你们发现哪里不对，欢迎指正——我们也在持续验证。

## 一、事件背景

2026-08 中旬，某账号被团结官方封禁（登录时 Unity ID authentication failed / 401）。
同期群里多名使用 ZCode + 反代的用户也被封。官方客服的公开口径：

> 「我们是通过 session 的签名 sp 来封的，cli 这块不动，就不会」

解读：**封号判定依据 = session（x-litellm-session-id）+ 签名（X-Codely-Signature）这套凭证链**。
只要请求携带的凭证链和官方 CLI 一致，官方不管流量从哪个客户端壳发出。

## 二、我们排查与修复的完整清单（按时间线）

### 阶段 1：请求头对齐（第一轮被忽视的方向）

**问题**：我们的请求头和官方 CLI 差异巨大。

| 项 | 我们原来 | 官方 CLI 真值 | 结论 |
|---|---|---|---|
| User-Agent | `codely-cli/1.0.0-release.52 (win32; x64)` | `codely-cli/1.0.0-rc.54 (win32; x64)` | 版本号+外壳格式都不对 |
| X-Codely-Signature | **没有** | 必须带，缺失返回 401 | 最关键的凭证链缺失 |
| x-litellm-session-id | 固定 | 每次请求随机 UUID | 固定会粘死坏实例 |

**修复**：
- UA 改为官方真值
- 补齐签名（算法下面单列）
- session 每次请求随机

### 阶段 2：签名算法逆向（核心中的核心）

官方签名算法（从 rc.54 bundle 逆向，逐字节复刻）：

```
种子 seed = 406f00f74768ba0cb0cd30f097ec6c2bdacb89c61a38b7dd140838bbd0e98018
密钥 k1 = HMAC_SHA256(seed, "codely-signing-v1")
签名密钥 signingKey = HMAC_SHA256(k1, cli_api_key)
消息 msg = "v1\n" + path + "\n" + timestamp   // 只签 path，不签 body
签名 sig = HMAC_SHA256(signingKey, msg)
头值 = "v1." + timestamp + "." + base64url(sig)  // base64url 无 padding
```

- cli_api_key 换取：`GET https://codely.tuanjie.cn/api/api-token/cli-api-key`，`Authorization: Bearer <oauth access_token>`
- 签名只签路径（如 `/v1/chat/completions`），**不签 body**

### 阶段 3：请求体重排（对齐官方 buildCreateParams）

官方发到 LiteLLM 的请求体字段顺序（buildCreateParams 展开）：

```
model, messages, [temperature], [max_tokens 系], [reasoning_effort], [top_p],
[metadata], [litellm_session_id], [prompt_cache_key],
[tools, parallel_tool_calls:true, tool_choice],
[stream:true, stream_options:{include_usage:true}]   // 仅流式
```

要点：
- **非流式请求不带 stream/stream_options 字段**（官方 delete 掉）
- 请求体 `litellm_session_id` / `prompt_cache_key` 与请求头 `x-litellm-session-id` **同值**
- 不要把 metadata 的 user_id 塞进去——那是官方 Anthropic 路径的形态，OpenAI chat 路径没有

### 阶段 4：UA 真相（最容易踩的坑，我们踩了）

**官方有两套 UA，别搞混**：

| 值 | 用途 |
|---|---|
| `codely-cli/1.0.0-rc.54 (win32; x64)` | **HTTP 请求真正的 User-Agent**（Dre/QEe 构造器 defaultHeaders，格式 `codely-cli/${版本} (${platform}; ${arch})`） |
| `Codely-CLI - OSS/1.0.0-rc.54 (Codely-Cli/1.0.0-rc.54)` | **telemetry 埋点字段**（getRealUserAgent，只出现在统计上报，不是 HTTP UA） |

我们曾把第二个（埋点字段）当 UA 用了很久，是独立代码审查才揪出来的。**服务端第一眼看到的就是 UA，这个错了等于自报家门。**

### 阶段 5：DashScope 头的正确用法（多即是错）

官方在聊天气息上**默认不发送** `X-DashScope-CacheControl` / `X-DashScope-UserAgent` 这两个头。

官方只在 `isDashScopeProvider()` 为真时才发：
- authType === QWEN_OAUTH
- 或 baseUrl 指向 `dashscope.aliyuncs.com`

**我们上游是 codely-litellm.tuanjie.cn，不满足条件——官方这条路线上根本不会带这两个头。** 我们一度无条件添加，等于主动挂反代标签，已删除。

### 阶段 6：TLS 指纹（Go 栈的隐藏身份）

Go 的 `http.Transport` 原生 TLS ClientHello 指纹和 Node.js（官方 CLI 运行时）完全不同。
服务端如果看 JA3/JA4，一眼就能区分。

修复：用 `github.com/refraction-networking/utls` 替换握手层，伪造成 Chrome/BoringSSL 系指纹
（HelloChrome_Auto，与 Node.js 的 BoringSSL 同源）。

**坑一（双层 TLS）**：不能简单在 DialContext 里返回已握手连接——Go 标准库检测到是 https 会再包一层 TLS。
正确做法是用 `DialTLSContext` 挂点，且**不设 Transport.Proxy**（设了会被绕开），自己管代理：
TCP 连代理 → CONNECT 隧道 → 隧道内 utls 握手。

**坑二（ALPN）**：HelloChrome_Auto 自带 h2+http/1.1 双 ALPN，协商出 h2 后标准库会往
h2-only 连接发 HTTP/1 请求导致断连。修复：把 ALPN 扩展**原位替换**为仅 `http/1.1`
（不要删除后 append 到末尾——JA3 按扩展序哈希，挪位会偏离 Chrome 真指纹）。

## 三、验证方式（我们是怎么确认修复有效的）

1. **真实流量 200**：修复后请求稳定 200，而签名错误时上游直接 401——200 本身就是凭证链被接受的最硬证据
2. **独立代码审查**：让一个不参与开发的审查者逐行比对我们的实现 vs 官方 bundle 源码
3. **抓包对照**：官方 CLI 和我们的反代各抓一次，对比请求形态（注意：TLS 加密下只能看到 SNI，HTTP 头得靠源码级比对）

---

## 四、仍然存疑/未解决的点（诚实清单）

1. **TLS 指纹是否真的是判定项**——我们没有证据证明官方看 JA3，只是"能对齐就对齐"的保守策略
2. **metadata 的 prompt_id 等字段**——官方 chat 路径 metadata 是 `{prompt_id, session_id, cwd}` 形态，
   我们没有完全复刻（请求里没有这些 id 时官方似乎也不带 metadata，暂按不带处理）
3. **流量行为层**（使用频率、并发、长连接模式）——官方理论上能看到，无法通过客户端对齐解决

---

## 五、给反代开发者的一句话总结

> **签名（X-Codely-Signature）+ session（x-litellm-session-id）是凭证链核心，必须与官方 CLI 逐字节一致；
> UA 用 HTTP 真值 `codely-cli/{version} (win32; x64)` 而不是埋点格式；
> 官方不发的头（DashScope）别多发；请求体字段顺序尽量对齐 buildCreateParams；TLS 指纹能伪装就伪装。**

以上只是我们的修复路径，不是唯一答案，欢迎验证与补充。
